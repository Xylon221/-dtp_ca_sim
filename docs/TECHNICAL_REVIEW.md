# 端口更新优化：项目技术复盘与面试准备

更新：2026-10-28。依据本仓库源码及本次实测整理。

## 1. 一分钟介绍

我关注的是周期精确模型中端口更新的调度开销。基线每周期检查全部端口，即使本周期只写了少量输入，也要付出全量扫描成本。我用“信号地址到模块更新回调”的哈希映射，在写入值真正变化时收集信号，再派发到相关模块。两个版本保留相同的通道计算和寄存器更新逻辑，通过完整最终状态比较与逐周期信号波形比较验证。在本仓库默认合成配置的一次运行中，耗时从 308.099 ms 降到 111.188 ms，约 2.77 倍。

这段介绍描述的是公开最小复现。原工作是否由本人完成、真实芯片规模和业务结果，需要结合本人经历回答；不能把此复现当作公司内部平台的完整开源。

## 3. 当前实现和原始工作背景

| 内容 | 当前仓库可验证的内容 |
| --- | --- |
| 建模框架 | `Signal / Module / PortBinding` 轻量 C++ CA 框架 |
| 多通道模型 | N 个通道，各有 6 输入、2 输出、R 个寄存器 |
| 优化对比 | `PollEngine` 与 `DispatchEngine` |
| RTL/SystemC | 独立单通道算术例子，20 周期逐点对比 |
| uniBench / 真实芯片 RTL | 未包含 |
| MPI / 前后门访问 | 未实现 |
| 自动 RTL→SystemC | 未实现；示例 SystemC 为手工模型 |

多通道基准有 addr/len/ctrl 等额外输入，单通道 RTL/SystemC 只有 data/mode/en 等输入。单通道对照通过，不等于证明整个多通道框架与真实 RTL 等价。

## 4. 数据结构与调用关系

`Signal` 保存信号值；`Module` 提供 `eval()` 与 `tick()`；`PortBinding` 保存模块指针与成员函数指针。

```cpp
using UpdateFn = void (Module::*)();
struct PortBinding { Module* m; UpdateFn fn; };
std::unordered_map<Signal*, std::vector<PortBinding>> map;
```

用 vector 保存绑定，是为了表达一个信号可能通知多个模块。信号对象由 `Chip` 内固定大小 vector 持有，注册回调后不再改变 vector 大小，因此地址在本次运行中稳定。

### 基线：轮询

每周期先写入 K 个通道，然后遍历所有 N×P 个输入端口，比较当前值与每端口 snapshot；变化时执行成员函数回调。

### 优化：收集变化并派发

每次写入先判断新旧值，只有实际变化才进入 `changed` 队列；本周期输入写完后，再对每个变化地址查哈希表并调用绑定回调。最后两版都对所有 N 个通道执行 `tick()`。

代码入口：`run_poll()`、`run_dispatch()`，核心数据结构见 `ca/dtp_ca.h`。

## 5. 为什么收益来自稀疏写入

设总输入端口数为 P_total，实际变化信号数为 C，变化信号总扇出为 F_changed：

```text
轮询端口阶段：O(P_total + F_changed)
派发端口阶段：平均 O(C + F_changed)
共同的寄存器更新：O(N×R)
```

哈希地址查找平均 O(1)，整个周期不是 O(1)。当信号连接多个模块时仍需遍历其绑定；碰撞严重时哈希最坏复杂度也会退化。

默认 N=2048、P=6、K=8，因此基线每周期检查 12288 个端口，优化版每周期最多处理 48 个变化输入。实际变化数可能小于 48，因为 en 或控制字段可能保持不变。

K 指每周期收到新写入的通道数，并不表示只有 K 个通道执行时序逻辑。模型里 en 被置 1 后不会自动清零，所有通道仍进入 tick。理解这点，才能解释 R 较大时端口优化的总体收益为何变小。

## 6. 调度语义与正确性风险

本次发布把旧代码“每写一个输入就立即派发”改为“全部输入写好，再派发变化地址”，使两版回调看到相同的本周期输入值，避免中间值干扰。

当前模型仍是一个受控 benchmark：没有通用的 delta-cycle 收敛、组合环检测、跨级事件传播或动态模块注销。寄存器更新后的组合重算也不模拟完整 SystemC 内核语义。不能直接推广为任意电路的正确事件仿真器。

若未来用于生产模型，应明确：

1. 同一信号一周期多次写入的合并规则。
2. 多个变化端口触发同一模块时是否去重及其语义。
3. 组合逻辑传播到下游的事件队列与收敛条件。
4. 模块销毁时如何注销回调，避免悬空指针。
5. 多线程写入时的数据竞争与调度顺序。

这些是后续方向，不是当前已实现功能。

## 7. 如何定位与测量

先用 gprof 确认轮询热路径，再用非 `-pg` 构建的 chrono 墙钟耗时评估整个运行函数。

当前计时从进入 `run_poll/run_dispatch` 前开始，到函数返回结束，包含端口注册和引擎容器构造/销毁；不包含 `Chip` 构造、最终状态比较和结果打印。启用 VCD 时还会包含文件输出，所以不能把波形运行当作性能基准。

`make profile` 使用 60000 周期、R=12；`make bench` 使用 20000 周期、R=1。两者配置不同，不可以用 profile 的百分比直接解释 bench 的全部加速比。

gprof 的 self-time 百分比是采样时间占比，不是进程总 CPU 利用率。0.00% 也不意味着函数没有耗时。

## 8. 本次验证证据

- 五种 N/K/R 组合覆盖 K=0、K=1、K=N、R>1；各 200 周期。
- 两版结束后直接逐项比较所有通道的全部寄存器、out 和 status，不只依赖 checksum。
- 两份 VCD 逐字节相等；有活动时必须存在时间采样，避免“两个空波形也相等”。
- 独立单通道 RTL/SystemC 与数学参考逐周期比较，20 个采样点全部一致，最终 accum=240。
- 拒绝周期数为零、N 为零、K>N、R 为零等无效尺寸。

VCD 是每周期末的信号采样，不覆盖周期内所有中间状态；最终寄存器相等也不单独证明任意内部过程等价。测试覆盖的是当前模型和激励。

本次默认 benchmark：308.099 → 111.188 ms，2.77×。独立 gprof 的轮询函数 self-time 占比 63.89%，派发函数占比 2.86%。详见 [原始记录](VALIDATION.md)。

## 9. 面试数据必须统一口径

旧材料包含“25.3%→8.1%、整体 2.5×”；旧复现曾写“59.1%→约 0%、2.67×”。这些不是本次结果，仓库不能证明原工作测量的背景。

尤其要考虑 Amdahl 定律：如果端口阶段确实占同一基线总耗时的 25.3%，且唯一变化只是把该阶段消除，整体理论上限是：

```text
S_max = 1 / (1 - 0.253) ≈ 1.34
```

因此“25.3% 与整体 2.5×”不能在没有其他解释时作为同一测量口径的因果结论。需要查原始测量是否使用不同任务、self/total time、不同范围，或者还有其他优化；没有证据就明确说待核实。

本次复现只给出当前配置的测量，不试图调参数凑出历史数字。

## 10. 常见追问

**为什么用信号地址做 key？** 对象地址稳定时无需比较信号名，能直接定位绑定回调；代价是必须保证对象生命周期和地址稳定。

**为什么不是数组直接索引？** 如果信号已有稠密稳定 ID，数组可能更快。哈希表适合稀疏地址和动态注册。本仓库展示地址映射方案，没有证明它优于所有其他结构。

**稠密活动还会快吗？** 不保证。C 接近总端口数时，哈希查询与队列开销可能高于顺序扫描，应随 K/N 扫描参数测量。

**为什么不只 tick 变化模块？** 时序状态不一定只由组合输入变化决定。改变 tick 范围需要另一个严格定义的调度优化与验证，当前保持两版一致。

**如何证明收益来自端口更新？** 使用相同 Chip、激励、eval/tick，改变端口调度机制；同时报告构建标志、参数和计时边界。注册容器也不同，因此小规模短运行会受到初始化开销影响。

**空间代价是什么？** 每个已注册信号的哈希节点、绑定 vector 和变化队列，占用更多管理内存；应同时看运行时间和峰值内存。
